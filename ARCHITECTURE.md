# suizo — Architecture

## Problem

Amateur club tournaments (chess opens, futbolito, table tennis) are still run on
paper or on a shared spreadsheet. Existing tournament software is either SaaS
priced for federations or heavyweight desktop apps. The organizer — often a
volunteer with a laptop, sometimes offline — needs to register players, pair
rounds under Swiss rules, take results at the table, and publish standings
without installing or operating anything.

Hard constraints:

- **Zero infrastructure.** One static binary, state in one JSON file. No server,
  no database, no account.
- **Data survives crashes.** The state file is replaced atomically; a partial
  write never destroys the tournament.
- **Stdlib only.** No web frameworks, no client build step. The dependency list
  of this project should stay boring.

Non-goals: online registration, payments, live broadcasting, federated
rankings, and multi-tenant anything.

## Big picture

Everything is a transformation of one in-memory `Tournament` document, persisted
by one `store`:

```text
                  load()                     save()  (atomic: tmp + rename)
  suizo.json  <---------  store  <---------  CLI command (main.go)
                             |                     |
                             v                     v
                        Tournament  <--------  domain ops
                        (tournament.go)       (pairing, standings, rounds)
```

Walkthrough — register a player: `suizo players add "Ana"` → `run()` resolves
the state file path (`$SUIZO_FILE` or `./suizo.json`) → `openStore` ensures the
parent directory → `store.load()` returns a fresh tournament if the file is
absent → `Tournament.addPlayer` validates and appends (`p<N+1>`) →
`store.save` marshals indented JSON to a temp file and renames over the target
→ the CLI prints the new id and exits 0.

Future faces of the same document: more CLI verbs (pair, results, standings)
and a `net/http` localhost view (`suizo serve`) that renders server-side
templates and POSTs back through the same domain operations. Both faces read
and write through `store`; neither touches JSON encoding directly.

## Code map

```text
suizo/
  main.go             # CLI dispatch: argv → command functions → exit code; no domain logic
  tournament.go       # Tournament/Player/Round/Match types + domain operations
  store.go            # load/save of the single JSON document; atomic writes
  errors.go           # sentinel errors returned by domain operations
  *_test.go           # table-driven tests, one file per subject
  docs/               # DECISIONS.md (why), FORMAT.md (state schema), agents docs
  tasks/              # work items (ArggonManager) — the in-tree tracker
  templates/          # work-item body templates used by `arggon create`
```

Domain logic must NOT live in `main.go`; JSON encoding must NOT leak outside
`store.go`.

## Boundaries and layering rules

- `main.go` → domain (`tournament.go`) → `store.go`; never the reverse.
- All state mutation goes through `Tournament` methods; commands do not edit
  slices directly.
- The on-disk schema is owned by `docs/FORMAT.md` — any field change updates
  that doc in the same PR.

## Invariants

- Concurrent single-process runs never corrupt the file (atomic rename) —
  guarded by `TestSaveLeavesNoTempFiles`; cross-process locking is tracked in
  issue #6.
- Player ids are stable and never reused — guarded by `TestNextPlayerID`.
- `players add` never accepts an empty name — guarded by `TestAddPlayer`.
